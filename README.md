# Factory Data Agent — 공장 데이터에 말로 묻고, 그럴듯한 오답을 잡는다

> 생산관리자가 "지난주 3라인 불량률 왜 올랐어?"라고 물으면 SQL로 답하는 에이전트.
> 어려운 건 답을 못 내는 게 아니라 **실행은 되고 숫자도 나오는데 틀린 답**이다.
> 이 저장소는 그런 오답이 어디서 생기는지 가상 공장 데이터에 함정을 넣어 재고,
> 의미 계층(지표 정의)과 검증기가 그것을 얼마나 막는지 로컬 7B 모델로 비교한다.

체험: `web/`(브라우저 안 DuckDB, 설치 없음) · 재현: `python -m fda.data` → `pytest` → `scripts/run_eval.py` → `scripts/report.py`

## 1. 목표·이유

Text-to-SQL 평가는 보통 "실행 정확도"를 본다. 그런데 업무 데이터에서는 실행 성공과 정답 사이에
큰 틈이 있다. 시각이 UTC로 저장돼 있는데 KST로 물으면, 작업지시 하나에 실적과 검사가 여러 건씩 붙어
있는데 둘을 한 번에 조인하면, 입고가 박스 단위로 섞여 있으면 — SQL은 문제없이 돌고 숫자는 그럴듯하다.
이 틈을 재는 것이 목표다.

## 2. 상품성

MES·ERP 데이터를 쓰는 현업(생산관리·품질·자재)이 SQL 없이 묻는 도구. 틀린 숫자가 보고서에 들어가면
SQL 오류보다 비싸다. 그래서 "답을 보류할 줄 아는" 에이전트가 필요하다.

## 3. 데이터 — 가상 공장(결정적 생성)

`fda/data.py`. 4라인·12설비·12제품·20자재, 91일. 함정 8종은 모두 테이블 설명·용어집에 적혀 있다(숨긴 규칙이 아니다).

| 함정 | 내용 |
|---|---|
| 시간대 | 시각은 UTC 저장, 질문은 KST |
| 야간조 | C조 22~06시, 근무일은 조가 시작한 날 |
| 1:N 부풀림 | 작업지시 1건에 실적·검사가 각각 여러 행 |
| 취소 작업지시 | 취소 전 시운전 실적이 남아 있음 |
| 단위 | 입고는 BOX(×pack_size)와 EA가 섞임 |
| 계획 정지 | 예방정비는 가동률에서 빼지 않음 |
| 진행 중 | end_ts NULL |
| 지표 정의 | 불량률은 공정 불량률, 비율의 평균이 아니라 합계의 비율 |

데이터 안의 사건: 지난주 3라인 프레스(E07) 비계획 정지 21회, 같은 주 3라인 불량률 0.075(평소 0.029).

## 4. 질문 세트

`fda/questions.py` — 12개 템플릿 82문항(대조군 포함), 정답 SQL은 의미 계층과 독립적으로 손으로 썼다.
템플릿 안에서 층화해 dev 30 / test 52. 판단·수정은 dev에서만 한다.
하네스를 디버깅하다 결과를 본 test 2문항은 dev로 옮겼다(`SEEN_IN_DEBUG`).

## 5. 비교하는 네 방식

| | 방식 |
|---|---|
| S0 | DDL + 현재 시각만 주고 SQL 생성 |
| S1 | + 테이블 설명·용어집 |
| S1V | S1 + 검증기(sqlglot 정적 규칙 9종 + 실행 결과) → 1회 재생성 → 그래도 걸리면 답 보류 |
| S2 | LLM은 지표·조건 JSON만, SQL은 의미 계층이 생성. 정의 밖 질문은 S1V로 |

검증기는 정답 SQL 82개 전부에서 규칙이 하나도 걸리지 않는 것(오경보 0)과, 함정 SQL 7종을 모두 잡는 것을 테스트로 고정했다.
의미 계층은 정답 의도(JSON)를 받으면 70문항 전부 정답 SQL과 같은 결과를 낸다(`tests/test_semantic.py`).

### 선택한 것과 이유

- **모델: Qwen2.5-7B-Instruct-AWQ(로컬 vLLM)** — 사내 GPU 한 장에 올라가고 데이터가 밖으로 나가지 않는 크기. 비교로 같은 크기의 SQL 특화 모델(Qwen2.5-Coder-7B-AWQ)을 붙였다.
- **DuckDB** — 파일 하나로 재현되고, 같은 엔진(WASM)이 브라우저에서 돌아 체험판이 서버 없이 같은 SQL을 실행한다.
- **PostgreSQL 16** — 운영 DB 쪽 확인. 의미 계층 SQL은 DuckDB 방언으로 만들고 sqlglot으로 옮긴다.
- **sqlglot** — 검증 규칙을 문자열이 아니라 파스 트리로 본다(어느 SELECT가 어느 테이블을 직접 조인하는지). 방언 변환도 같은 도구.
- **의미 계층을 직접 구현** — dbt·Cube 같은 도구 대신 지표 11개를 파이썬 함수로 두었다. 무엇이 함정을 없애는지(조인을 LLM이 쓰지 않는 것) 그대로 보이게 하려고.

## 6. 결과 — test 52문항, Qwen2.5-7B-Instruct-AWQ(로컬 vLLM, temperature 0)

**정답 판정은 두 데이터에서 한다.** 첫 dev 집계에서 검증기 "오경보" 4건을 열어 보니, 시간대 변환을 빠뜨린 SQL이
우연히 정답과 같은 값을 낸 것이었다(입고 09:00 KST = 00:00 UTC라 날짜가 안 바뀜). 그래서 기록 시각을 날짜 경계 쪽으로
옮긴 두 번째 데이터(`data.stress`)를 만들고, 예측 SQL을 거기서도 다시 돌려 정답 SQL과 같아야 "정답"으로 센다.
한쪽에서만 맞은 것은 "우연히 맞음"으로 따로 센다.

| 방식 | 정답 | 그럴듯한 오답 | 실행 오류 | 답 보류 | 정답률 | 응답 p50 |
|---|---|---|---|---|---|---|
| S0 DDL만 | 4 | 27 | 21 | 0 | 7.7% | 0.68s |
| S1 + 설명·용어집 | 15 | 21(우연 1 포함) | 16 | 0 | 28.8% | 0.92s |
| S1V + 검증기 | 11 | **4** | 15 | 22 | 21.2% | 2.32s |
| **S2 의미 계층** | **50** | **0** | 1 | 1 | **96.2%** | 0.48s |

- **실행 성공률은 정답률이 아니다.** S0는 52문항 중 31개가 실행됐지만 그중 27개(87%)가 틀린 값이었다.
- **규칙을 글로 주는 것으로는 부족하다.** S1은 용어집에 "UTC 저장"·"취소 제외"가 적혀 있는데도 시간대 7/38, 취소 2/21만 맞혔다.
- **검증기는 오답을 막지만 답도 막는다.** 첫 SQL 기준으로 틀린 37개 중 33개를 잡았고(규칙별: 시간대 32·취소 11·부풀림 4),
  맞은 15개 중 6개를 잘못 막았다. 재생성 1회로 고쳐지는 경우는 적어 보류가 22건이 됐다 — 틀린 숫자 21건이 4건으로 줄고 정답은 15→11.
- **의미 계층은 함정을 구조로 없앤다.** LLM이 조인·시간대·단위를 직접 쓰지 않으니 남는 실패는 "의도를 잘못 고르는 것"뿐이고,
  그것도 재선택·조건 누락 검사로 막아 test에서 틀린 숫자가 한 건도 나가지 않았다(실패 2건은 오류·보류).
- 응답 시간은 같은 데스크톱 GPU를 다른 프로그램과 나눠 쓴 상태의 값이라 참고용이다.
- 짝지음 검정(정확 McNemar): S2 vs S1 불일치 **35:0, p=5.8e-11**. 검증기는 S1의 그럴듯한 오답을 19건 없애고 2건 새로 만들었다(p=2.2e-4).

### SQL을 더 잘 쓰는 모델로 바꾸면? — Qwen2.5-Coder-7B-Instruct-AWQ

| 방식 | 일반 7B 정답률 | Coder 7B 정답률 | Coder 그럴듯한 오답 |
|---|---|---|---|
| S0 | 7.7% | 5.8% | 30 |
| S1 | 28.8% | 19.2% | 20 |
| S1V | 21.2% | 15.4% | 4 |
| S2 | 96.2% | 96.2% | 2 |

SQL 특화 모델로 바꿔도 자유 SQL은 나아지지 않았다(S1 시간대 2/38, 일반 대 Coder 불일치 5:0, p=0.06으로 유의하지는 않음).
틀리는 이유가 SQL 문법이 아니라 **이 공장의 규칙(UTC 저장·취소 제외·BOX 환산)을 모른다는 것**이라, 모델을 키우거나 바꾸기 전에
규칙을 코드(의미 계층)로 옮기는 쪽이 효과가 컸다. Coder의 S2 오답 2건: 하나는 "라인별"인데 `group_by`를 빼 전체 합 한 줄을 낸 것, 하나는 의도를 만들지 못해 자유 SQL 경로로
넘어간 뒤 검증기를 통과한 오답이다(의미 계층 밖으로 나가면 다시 S1V 수준이 된다).

| 판 | dev 정답 | 바꾼 것(계기) |

### 운영 DB에서도 같은 답인가 — PostgreSQL 16

같은 데이터를 PostgreSQL에 COPY로 올리고(인덱스 7개), 정답 SQL과 의미 계층 SQL을 sqlglot으로 PostgreSQL 방언으로 옮겨 실행했다.
**정답 SQL 82/82, 의미 계층 SQL 70/70이 DuckDB와 같은 답**(`scripts/pg_parity.py`, `results/pg_parity.json`).

### 브라우저 체험판

`web/` — DuckDB-WASM이 parquet 10개(약 120KB)를 받아 모든 SQL을 그 자리에서 실행한다. LLM이 쓴 SQL과 고른 의도는 위 실행의 기록을 재생한다.
`?selftest=1`: 정답 SQL 82/82가 파이썬과 같은 결과, 검증기 브라우저판(정규식 근사)은 파이썬판(sqlglot)과 규칙 판정 201/210 일치 —
어긋난 9건은 전부 sqlglot이 파싱하지 못한 SQL이다.

## 에러와 대처

1. **하네스를 디버깅하다 test 문항 결과를 봤다** — 스모크 3문항 중 2개가 test였다. 보고용 test에서 빼 dev로 옮겼다(`SEEN_IN_DEBUG`).
2. **채점이 너무 엄격했다** — 값 하나를 묻는데 `('L1', 1490)`처럼 라벨 열이 붙으면 오답으로 셌다. 측정 전에 "한 행이고 그 안에 정답 값이 있으면 정답"으로 고정했다.
3. **검증기 오경보** — 모델이 `DATEADD('hour', -9, ...)`로 경계를 옮긴 것을 시간대 규칙이 못 알아봤다. 정규식을 넓혔다.
4. **우연히 맞은 SQL** — 위 결과 절. 두 번째 데이터로 판정을 바꿨다. 그래도 남은 오경보 1건은 구조적이다: 야간조(22~06시 KST)의 실적은 UTC 날짜가 늘 조 시작일과 같아, 변환을 빼도 C조 질문에는 항상 맞는다.
5. **생성이 초당 5토큰** — 같은 GPU를 게임이 쓰고 있었다. 정답 판정(temperature 0)에는 영향이 없어 그대로 두고, 응답 시간은 참고값으로만 적었다.
6. **WSL에서 `pkill -f "vllm serve"`가 자기 셸까지 죽였다**(종료 코드 15) — 패턴이 자기 명령줄과도 맞는다. 서버가 내려간 것은 GPU 메모리로 확인했다.

## 개발 순서

데이터·함정 → 질문 82개와 정답 SQL → 의미 계층 + "정답 의도면 정답 SQL과 같은 결과" 테스트(70/70) → 검증기 + "정답 SQL엔 규칙이 안 걸림" 테스트(82/82) →
실행기(4방식) → dev v1~v4 → 두 번째 데이터로 판정 강화 → test → PostgreSQL 대조 → 브라우저 체험판.

## 7. 정직한 범위

- 데이터는 가상이다. 함정은 실제 MES에서 반복되는 모양을 따랐지만 내가 넣었고, 검증기 규칙도 그 함정을 알고 썼다 —
  **처음 보는 함정에 대한 검증기의 일반화는 재지 않았다.** 의미 계층은 정의된 지표 밖의 질문을 자유 SQL로 넘긴다.
- 질문은 12개 템플릿 82문항이고 한국어다. 모델은 7B 두 종(일반·코드)뿐이다.
- 검증기의 재생성은 1회다. 보류된 답을 사람이 어떻게 처리하는지는 다루지 않았다.
